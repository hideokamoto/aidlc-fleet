## Contribution

品質エンジニアの観点から、ドラフトの Testing Posture 節に対する追加の分析と、
インタビューで埋めるべきギャップを以下に記す。

### 1. リスクベースのテスト重点領域（M2/M3/M4 が最優先）

`intent-backlog.md` と `scope-document.md` を確認した。このプロジェクトの品質
リスクは一様ではなく、3 つの横断的コントラクトに集中している:

- **M2（四条件成功判定契約）**: `compose` exit 0 単独では不十分、`.drops` 内
  の `[degraded]` 検出、`doctor` の失敗数から `known_failures` を差し引いた値
  がゼロであること、`plugin sync` の exit 1 を "incomplete" として可視化する
  こと、の 4 条件の**論理積**。v0.1 文書自身が「最重要」と明言しており、
  `init`/`update`/`plugin add` すべてがこれに依存する。ここは行カバレッジ
  80% を満たしても、4条件のうち1つでも独立して壊れるケース（例:
  `[degraded]` が1件だけ混在、`known_failures` が丁度ゼロ差し引きになる境界、
  `plugin sync` が exit 1 だが他の3条件は成功、等）を見落とせば実害が出る。
  **境界値・組み合わせテスト（decision table / pairwise）を明示的な方針として
  テスト戦略に書くべき**であり、行カバレッジ床だけでは検出力を保証できない。
- **M3（origin-record version gate）**: reject/manual/none の migration-
  boundary 判定と `--acknowledge-migration` の相互作用。境界（gate 直前・
  直後のバージョン、`engine_origin` 欠損時の挙動）を明示的にテストマトリクス
  化すべき。
- **M4（file-ownership invariants）**: エンジン所有ディレクトリの `--force` +
  バックアップ、settings/hooks のマージ規則、`aidlc/` 不可侵（メモリシード
  複製を除く）、シンボリックリンク書き込み禁止、レシート外ファイルの自動削除
  禁止。これは**実ファイルシステムに対する統合テスト**（一時ディレクトリを
  使った実際の書き込み・マージ・削除の検証）が必須で、モックだけでは検出でき
  ない不変条件（特に「削除しない」「シンボリックリンクを書かない」）がある。

これら3つは Bolt 順序上も先頭（scope-document.md の Sequencing Preference）
に来るため、テスト基盤（フィクスチャ、一時ディレクトリヘルパー、アサーション
ユーティリティ)を最初の Bolt で確立する必要がある。

### 2. テストツールチェーンの未決定（ドラフトに記載なし）

ドラフトの Code Style 節は ESLint/Prettier に触れているが、**テストランナー
自体の選定**（`bun test`（bun 組み込み）、Vitest、Jest 等）と**カバレッジ計
測ツール**（`bun test --coverage` か `c8`/`istanbul` 系か）がどこにも書かれ
ていない。プロジェクトは bun/TypeScript の greenfield CLI であるため、
`bun test`（組み込み、追加依存なし）が自然な既定候補だが、これは提案であり
インタビューで確認が必要。CI での 80% カバレッジ床を「メカニカルに強制する
仕組み」（`bun test --coverage` の閾値失敗設定、または別ツール）も未決定。

### 3. マルチハーネス・マトリクステスト戦略が抜けている

このCLIは5ハーネス（Cursor, Kiro, Codex, opencode, Copilot）を横断する配布
基盤である。ドラフトのテスト方針には、ハーネスごとの相違（ファイル配置、
sessionStart フック形式、settings/hooks マージ規則の差）をどうテストするか
の言及がない。単一ハーネスに対する単体テストだけでは、他ハーネスでの回帰を
検出できない。**ハーネスごとのフィクスチャ（最小限のディレクトリレイアウト
サンプル）を用意し、共通コントラクト（M2/M3/M4/M8）をハーネス横断でパラメタ
ライズド実行する**ことをテストデータ戦略として明記すべき。

### 4. Exit-code contract（M8）はコマンド横断の契約テストが必要

`init`/`update`/`check`/`plugin add|remove`/`pin|unpin`/`status`/`doctor` の
全コマンドが 0/1/2/3/4 の exit code 契約を守る必要がある(v0.1 §8)。個々のコ
マンド単体テストとは別に、**「exit code 契約」を横断的に検証する契約テスト
スイート**（各コマンド × 各エラーシナリオで期待 exit code を一覧化）を設ける
ことを提案する。CI のスクリプト連携先（`check` を CI で直接使う想定、
scope-document.md 記載）にとって exit code の安定性は特に重要。

### 5. CI 品質ゲートの具体化が不足

ドラフトの Deployment 節は「配布物リリース」への読み替えを提案しているが、
CI パイプラインでのテスト実行ゲート（PR マージ前に `bun test` + lint +
coverage 閾値を必須化するか）が明示されていない。org.md の Code Style 節は
「リンタは CI で実行し失敗は PR をブロック」を既定としており、これをテスト
実行にも同様に適用する（テスト赤 = マージブロック）ことを Testing Posture 節
に明記すべき。

### 6. Methodology（test-after vs TDD）はリスク集中領域に限り再検討の余地

ドラフトは org.md 既定の test-after を踏襲する提案だが、M2/M3/M4 のような
「壊れたら実害が大きい」契約ロジックについては、テストファースト（先にテスト
ケース・境界値表を書いてから実装する）の方が仕様の曖昧さを早期に検出できる。
ただし全面 TDD 化はチームの合意事項であり、品質エージェントとしては
「M2/M3/M4 は最低限テストケース設計（境界値表）を実装前に完了させる」という
折衷案をインタビューの選択肢として追加することを推奨する（全面 TDD 強制の主
張ではない）。

## Positions

- AGREE: greenfield ゆえ org.md の既定スコープ床がそのまま機械適用できず、
  `mvp`/`feature` 相当の 80% ライン・カバレッジ + マージ前 CI green を暫定
  採用する、というドラフトの判断 — 基盤ツールとしての堅牢性要求に照らして
  妥当な出発点であり、他に選ぶべき既定床もない。
- AGREE: M2（四条件成功判定）をテスト方針に明記すべきというドラフトの
  インタビュー論点3 — 品質エージェントとして最優先で支持する。ただし単なる
  「明記すべきか」の可否確認にとどめず、具体的な境界値・組み合わせテスト
  マトリクスの要求として深掘りするべき。
- OBJECT: ドラフトの Testing Posture 節は「行カバレッジ床」のみを議論して
  おり、テストランナー／カバレッジ計測ツールの選定（`bun test` か他か）が
  一切触れられていない — greenfield で技術選定がまだない以上、テストツール
  チェーンの決定はインタビューの必須論点として追加すべき。
- OBJECT: マルチハーネス（Cursor/Kiro/Codex/opencode/Copilot）横断のテスト
  データ戦略（ハーネスごとのフィクスチャ、パラメタライズドテスト方針）が
  ドラフトのどの節にも存在しない — この CLI の存在意義そのものがマルチ
  ハーネス配布である以上、単一ハーネスのみでの検証は重大な見落としになり得る。
  インタビューで確認すべき論点として追加を要望する。
- OBJECT: M4（ファイル所有権不変条件: シンボリックリンク非書き込み、レシート
  外ファイル削除禁止等）は実ファイルシステムに対する統合テストが必須である
  旨がドラフトに明記されていない — 単体テスト（モック）だけでは検出できない
  クラスの不具合（誤削除・シンボリックリンク書き込み）であり、テスト方針に
  「M4 は実ファイルシステム上の統合テストで検証する」という一文を追加すべき。
- OBJECT: Exit-code contract（M8）がコマンド横断の契約であるにもかかわらず、
  ドラフトはコマンド単位のテストのみを前提としているように読める — 契約テ
  ストスイート（コマンド × シナリオ × 期待 exit code の一覧）を独立した成果
  物として位置付けるべき。
